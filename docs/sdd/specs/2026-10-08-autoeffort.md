# autoeffort — design

**Date:** 2026-10-08
**Status:** agreed

## 1. Problem
Стандартний режим effort `auto` у Claude Code має мало налаштувань і непрозорий: не видно, який рівень обрано для конкретного запиту і чому. Різні етапи роботи потребують різної глибини міркування: збір контексту не вимагає максимуму, а аналіз, планування і перевірка, навпаки, вимагають. Зараз або все йде на одному рівні (переплата чи недодумування), або рівень доводиться перемикати вручну. Скіли можуть задавати власний effort, але немає способу поєднати його з власною логікою вибору.

## 2. Constraint that shapes the solution
Effort задається **на запит до моделі** (`turn.step`), а не на інструмент. Read чи Edit самі не міркують: effort визначає, як глибоко модель думає, коли вирішує наступну дію. Мод не знає наперед, що модель зробить у цьому кроці, тому фазу треба визначати до запиту з двох джерел:
- **маркер фази**, який модель оголосила в попередньому кроці (вона знає свій намір);
- **правила** за історією викликів інструментів (резерв, коли маркера немає).

Тому обрано A + C. Класифікатор-модель (haiku на кожен крок) відкинуто: це затримка і вартість на кожен запит і знову непрозорі рішення.

Друге обмеження: скіл не передає свій effort окремим полем. У `turn.step` приходить лише підсумковий `e.effort`, тож межу скіла визначаємо як відхилення від базового рівня сесії.

## 3. Solution

### 3.1 Рівні
Використовуються лише `medium`, `high`, `xhigh`, `max`. Рівень `low` не використовується: будь-який обчислений чи вхідний `low` піднімається до `medium` (підлога).

### 3.2 Фази і типові рівні
| Фаза | Маркер | Рівень |
|---|---|---|
| збір контексту | `⟦phase:gather⟧` | medium |
| аналіз і планування | `⟦phase:plan⟧` | xhigh |
| реалізація | `⟦phase:implement⟧` | medium |
| перевірка | `⟦phase:verify⟧` | xhigh |

Рівні фаз задаються в конфігу (`userConfig`).

### 3.3 Обчислення effort для запиту (`decide`)
Для кожного `turn.step` у треді (основний або субагент, ключ — `agentId ?? "main"`):
1. **Фаза.** Якщо в попередньому кроці цього треду був валідний маркер, береться він (маркер діє на один наступний крок). Інакше правила `classify`:
   - перший крок ходу (`index === 0`) → `plan`;
   - останні виклики — лише Read, Grep, Glob, LS, WebFetch, WebSearch → `gather`;
   - перший Edit/Write/NotebookEdit після серії з ≥ 3 читань без редагувань → `plan` (крок, на якому модель вирішує, що змінювати);
   - останні виклики містять Edit, Write, NotebookEdit → `implement`;
   - Bash, чия команда відповідає патернам verify (`test`, `jest`, `vitest`, `pytest`, `lint`, `eslint`, `tsc`, `build`, `typecheck`, `cargo check|test`, `go test`; список у конфігу), після хоча б одного редагування в ході → `verify`;
   - інакше — фаза попереднього кроку треду, а якщо її немає, `plan`.
2. **Рівень фази** за таблицею 3.2.
3. **Нижня межа скіла чи агента.** Межа — це:
   - рівень `e.effort`, якщо він відрізняється від базового рівня сесії, запам'ятованого на першому кроці основного треду в цьому ході (так проявляється effort зі скіла);
   - для субагента — явний `effort` з виклику Agent, що його запустив.
   Рівень = max(рівень фази, межа).
4. **Підлога** `medium`.

Результат: `{ level, phase, source: "marker" | "rule:<name>", floor?: "<skill|agent>:<level>" }`.

### 3.4 Маркери (частина C)
- `prompt.compose` додає в кінець системного промпту секцію (`scope: 'session'`): на початку кожної відповіді, перед викликами інструментів, оголоси одним маркером, чим займатимешся в наступному кроці після цих результатів: `⟦phase:gather|plan|implement|verify⟧`.
- `turn.step` пропускає текстові шматки через `marker`, який знаходить маркер навіть розірваним між шматками, вирізає його з тексту (його не видно ні на екрані, ні в історії) і повертає фазу. Невалідний маркер вирізається і ігнорується.

### 3.5 Модулі
| Файл | Відповідальність | Інтерфейс | Залежить від |
|---|---|---|---|
| `src/levels.ts` | порядок рівнів, max, підлога | `maxLevel(a,b)`, `applyFloor(l)` | — |
| `src/classify.ts` | історія → фаза за правилами | `classify(history, ctx) → {phase, rule}` | — |
| `src/marker.ts` | потоковий пошук і вирізання маркера | `createMarkerFilter() → {push(text) → text, flush() → text, phase}` | — |
| `src/decide.ts` | поєднання 3.3 | `decide(input, config) → Decision` | `classify`, `levels` |
| `src/config.ts` | типові значення + `userConfig` | `loadConfig(options) → Config` | — |
| `hooks/register.ts` | з'єднання з рушієм: `prompt.compose`, `tool.call`, `turn.step`, `skill.prompt`, `session.start`, `command.run` | `register` | усе вище |
| `types/index.d.ts` | контракт `$.state` (`threads`, `log`, `enabled`, `baseline`) | — | — |

### 3.6 Прозорість
- Статус-рядок після кожного рішення: `⚙ <level> · <phase> (<source>)`, наприклад `⚙ xhigh · plan (marker)`, а з межею: `⚙ high · gather (rule:read) ↑skill`.
- `/autoeffort` — стан (увімкнено чи ні, базовий рівень, фаза кожного треду) і останні 20 рішень.
- `/autoeffort on|off` — увімкнути чи вимкнути без перезапуску; вимкнений мод нічого не переписує і не додає секцію промпту.
- `/autoeffort log` — повний лог рішень сесії (`$.state`): час, тред, крок, вхідний effort, підсумковий рівень, фаза, джерело, межа.

### 3.7 Збої
- Помилка в будь-якому хуку → `next(e)` з незміненим входом (fail-open), рядок про помилку в лозі.
- Модель без підтримки effort (немає `e.effort`) → мод не втручається.
- Модель не оголосила маркер → працюють правила.
- Мод вимкнено → повністю прозорий.

### 3.8 Підключення
Мод лежить у репо `autoeffort` (`.claude-plugin/plugin.json`, `hooks/hooks.json`, `hooks/register.ts`, `src/*`, `types/index.d.ts`). Локально він підключається через `claude --plugin-dir /home/pc/projects/my-cc-mods/autoeffort` або постійно через `CLAUDE_CODE_PLUGIN_DIRS`.

## 4. Out of scope
- Класифікатор фаз на моделі (haiku) — можливе розширення пізніше.
- Керування вибором моделі (лише effort).
- Панель або дашборд; лог у файл між сесіями.
- Читання frontmatter скілів з диска (межа визначається через `e.effort`).
- Рівень `low` у будь-якому вигляді.

## 5. Trade-offs accepted
- Правила дивляться на минулі дії, тож на межі фаз можливий один крок з неточним рівнем. Маркер це зменшує, але не усуває.
- Маркер залежить від дисципліни моделі; якщо вона його пропускає, якість падає до рівня правил, а не нижче.
- Секція промпту додає кілька десятків токенів до кожного запиту.
- Межа скіла визначається непрямо: якщо скіл задає рівень, що збігається з базовим, межу не видно. На результат це не впливає, бо тоді він дорівнює базовому.
- Відмова від `low` робить прості кроки дорожчими, ніж могли б бути. Це свідомий вибір на користь якості.

## 6. Verification
- `claude plugin validate .` — без помилок.
- `tsc -p .` — без помилок типів.
- `claude plugin test .` — проходять тести:
  - `classify`: кожне правило 3.3 і пріоритет між ними;
  - `marker`: маркер цілий, розірваний між 2–3 шматками, невалідний, відсутній; текст навколо не змінюється;
  - `decide`: маркер має пріоритет над правилом; межа скіла піднімає рівень; підлога `low → medium`; окремий стан для субагентів;
  - `register`: без `e.effort` хук нічого не змінює; помилка всередині → незмінений `next(e)`; `/autoeffort off` вимикає переписування і секцію промпту.
- Ручна перевірка: `claude --plugin-dir …` на невеликій задачі «прочитай → зміни → прогони тести». Статус-рядок проходить medium → xhigh → medium → xhigh, маркерів не видно у виводі, `/autoeffort log` показує рішення з причинами.
